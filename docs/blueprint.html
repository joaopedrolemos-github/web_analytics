Pulso Commerce

Um lakehouse de ponta a ponta para um e-commerce web brasileiro: dados brutos de pedidos, catálogo, logística e navegação chegam ao Databricks, passam por Bronze, Silver e Gold, viram métricas governadas na camada semântica e são consumidos por três frentes: Power BI com RLS, um dashboard HTML feito com Claude/Lovable e chatbots que respondem perguntas de negócio.

Orquestração

Um Lakeflow Job diário: gera arquivos novos → roda o pipeline declarativo (Bronze→Gold) → atualiza metric views → dispara refresh do Power BI via API.

Qualidade de dados

Expectations no Silver (DROP ROW e WARN), testes de unicidade de chave no Gold e uma tabela ops.dq_resultados que alimenta o painel de observabilidade.

CI/CD

Databricks Asset Bundles com ambientes dev e prd, deploy via GitHub Actions a cada merge na main. Isso mostra maturidade de engenharia para recrutadores.

RLS dinâmico

Tabela sec_acesso_regional (email, UF) relacionada a dim_geografia. Uma única role filtra pelo usuário logado.

[email] = USERPRINCIPALNAME()

Segunda role, Seller, filtra dim_seller[email_seller], para que cada seller veja só os próprios pedidos. Teste com “Exibir como” e mostre isso em GIF no README.

Como os dados chegam ao app

  • Lovable (React) chama uma Edge Function do Supabase
  • A função usa o token do sp_chatbot e chama a SQL Statement Execution API do Databricks
  • Consultas fixas e parametrizadas sobre as metric views; nada de SQL vindo do navegador
  • Cache de 1 hora para não acordar o warehouse a cada clique

Alternativa 100% Databricks

Publicar o mesmo front como Databricks App (Streamlit, Dash ou React). Mostra que você sabe entregar dentro da plataforma, com a autenticação e as permissões do Unity Catalog.

Versão Claude

Exporte um snapshot JSON das metric views e peça ao Claude um dashboard HTML de página única. Bom para um “relatório semanal de growth” publicado como link e anexado ao README.

Como funciona por dentro

  • System prompt com o glossário de métricas (exportado do Unity Catalog) e regras de resposta
  • Tool consultar_metricas: Claude escolhe metric view, medidas, dimensões e filtros em JSON
  • O backend monta o SQL com MEASURE(); o modelo nunca escreve SQL livre
  • Service principal só lê semantic; limite de linhas e timeout
  • Tool gerar_grafico devolve spec para o front renderizar
  • Log de perguntas em ops.chat_log para avaliar acurácia
{
  "name": "consultar_metricas",
  "input_schema": {
    "metric_view": "mv_vendas | mv_logistica | ...",
    "medidas":     ["GMV", "Ticket Médio"],
    "dimensoes":   ["Mês", "UF"],
    "filtros":     [{"campo": "UF", "op": "=", "valor": "RJ"}]
  }
}

Genie Space (nativo)

  • Fontes: as 4 metric views + dim_data
  • Instruções: “ano fiscal = ano civil”, “GMV exclui cancelados”, “responda em PT-BR”
  • Trusted assets: 5 consultas SQL validadas para perguntas frequentes
  • Benchmarks: 20 perguntas com resposta esperada para medir acurácia

Perguntas para a demo

  • Qual categoria mais cresceu em 2018?
  • Quais sellers estão com nota abaixo de 3,5 e atraso acima de 10%?
  • Qual canal traz clientes que mais recompram?
  • Quanto do GMV vem de clientes Campeões no RFM?
  • Compare o prazo de entrega do Norte com o do Sudeste.

Avaliação

Rode as mesmas 20 perguntas nos dois bots e publique a tabela de acurácia no README. Comparar Genie e Claude com números é um diferencial raro em portfólio.
